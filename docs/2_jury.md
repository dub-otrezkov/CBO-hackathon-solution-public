# 2. Инструкция для жюри

## Запуск на записи rosbag

Сначала соберите пакеты, как описано в [разделе 1](1_package.md). Дальше понадобятся два терминала. В обоих подключите ROS 2 и собранный workspace решения. Плееру `ros2 bag play` тоже нужен наш пакет `tram_vehicle_msgs`: без него плеер не знает тип `DriverControllerCommand` и пропускает топик контроллера.

```sh
# терминал 1: нода
source /opt/ros/humble/setup.bash && source install/setup.bash
ros2 launch tram_odometry tram_odometry.launch.py

# терминал 2: запись, в реальном времени
source /opt/ros/humble/setup.bash && source install/setup.bash
ros2 bag play -d 2 <папка записи>
```

Порядок запуска:
1. Запустите ноду и дождитесь строки `estimator params …; gnss_init_s=5.0; maps=loaded from …`. К этому моменту карты загружены.
2. Запустите `ros2 bag play` с ключом `-d 2`. С ним плеер сначала создаёт издателей, ждёт 2 с и только потом начинает проигрывание. Это важно из-за начала записи: в проверочной записи `30618_88aea4d9` за первые 0.4 с плеер публикует около 370 сообщений с метками первых ~4 с, в том числе GNSS. Подписки ноды обнаруживают издателей плеера не сразу, и без паузы эта пачка может до ноды не дойти. Ожидание перед запуском плеера здесь не помогает, потому что издатели плеера появляются только вместе с ним. В 3 из 10 наших прогонов без паузы пачка до ноды не дошла: нода начала работу с метки примерно на 5 с позже начала записи, и 3D-ошибка положения по скрипту организаторов выросла с 1.05–1.06 до 1.11–1.15 м. С `-d 2` мы сделали 3 прогона, пачка дошла во всех.
3. Когда запись закончится, остановите ноду: Ctrl+C в терминале 1. Нода завершается штатно.
4. Следующую запись проигрывайте в новом запуске ноды. Ключи `--loop` и `--start-offset` не используйте: нода ищет начальную точку по GNSS первых секунд записи и не ждёт, что метки времени пойдут по кругу.

Одна запись — один запуск ноды. Начальное положение нода находит по GNSS один раз после старта, в окне 5 с от первого сообщения GNSS. Потом окно закрывается до перезапуска. Если проиграть вторую запись в уже работающую ноду, привязки по GNSS не будет, и оценка продолжится из состояния, в котором закончилась первая поездка.

Параметр `use_sim_time` и топик `/clock` не нужны: нода считает время по меткам `header.stamp` входных сообщений.

## Проверочный скрипт организаторов и пакет сообщений

Скрипт организаторов `hackathon_solution_checker` поставляется со своей копией пакета `tram_vehicle_msgs`. В ней есть только `VelocitySensor.msg`, байт в байт такой же, как у нас, а типа `DriverControllerCommand` нет. Наша нода подписана на `/vehicle/driver_position_cmd` именно этого типа. Поэтому:
- решение собирайте с нашим `src/tram_vehicle_msgs`, в нём есть оба типа;
- скрипт организаторов с их пакетом собирайте в отдельном workspace. Два пакета с именем `tram_vehicle_msgs` в одном workspace colcon не принимает и останавливается с ошибкой о дублирующемся пакете. Файл `VelocitySensor.msg` у двух пакетов одинаковый, поэтому скрипт из своего workspace читает `/result/velocity` решения;
- если удобнее один workspace, удалите из него копию `tram_vehicle_msgs` организаторов и положите рядом с `checker_ros` наши `src/tram_vehicle_msgs` и `src/tram_odometry`. Так мы тоже проверяли: собрались все 3 пакета, скрипт посчитал метрики;
- `ros2 bag play` запускайте в терминале с workspace решения, как в командах выше.

Так мы запускали скрипт организаторов на их проверочной записи `30618_88aea4d9` с кодом из этой папки. Среднеквадратичная ошибка (RMSE) 3D-расстояния по положению получилась 1.053 м (максимум 13.17 м), RMSE скорости 0.055 м/с, сопоставлено 38 438 выходов. В прогонах, где нода не получила стартовую пачку записи (см. шаг 2 выше), было 1.11–1.15 м и 38 355 выходов.

Если решение собрано только с пакетом организаторов, нода всё равно запустится и напишет в лог предупреждение `tram_vehicle_msgs has no DriverControllerCommand: /vehicle/driver_position_cmd not used, wheels only …`. Тогда она работает только по тележкам, и модель тяги не получает позицию контроллера. Одни тележки дают меньше 10 выходов в секунду. Поэтому, если 0.05 с не было выхода, нода публикует оценку, продолженную от последнего выхода по его скорости и ускорению, с меткой последнего выхода плюс прошедшее время. Выходы идут примерно 20 раз в секунду. На записи `30618_88aea4d9` в этом режиме скрипт организаторов дал RMSE положения 1.088 м при частоте 19.98 Гц; этот прогон сделан на более ранней версии кода с теми же выходами.

## Что публикует нода

Нода публикует оценку на каждую новую метку времени входа. Сообщения передней и задней тележек с одинаковой меткой обрабатываются вместе и дают один выход. Если второе сообщение пары не пришло, первое ждёт его не дольше примерно 60 мс по системным часам. Каждая тележка присылает около 10 сообщений в секунду, контроллер 20, поэтому выходы идут около 30 раз в секунду. `header.stamp` выхода равен метке входного сообщения из записи, после которого выход посчитан. Исключение — режим без типа `DriverControllerCommand`, описанный выше. Одна и та же метка дважды не публикуется.

| Топик | Поле | Содержимое |
|---|---|---|
| `/result/velocity` (`tram_vehicle_msgs/msg/VelocitySensor`) | `header.frame_id` | `base_link` |
| | `velocity` | продольная скорость, м/с, не меньше нуля |
| `/result/position` (`nav_msgs/msg/Odometry`) | `header.frame_id` | `map` |
| | `child_frame_id` | `base_link` |
| | `pose.pose.position` | x, y, z точки `base_link`, м |
| | `pose.pose.orientation` | курс вдоль пути: поворот вокруг оси z, заполнены только `z` и `w` |
| | `pose.covariance` | элементы [0], [7], [14] (x, y, z) равны дисперсии пути вдоль рельсов из фильтра, м²; эта продольная дисперсия записана во все три оси без поворота; остальные элементы, в том числе для ориентации, равны 0 |
| | `twist.twist.linear.x` | скорость, м/с |
| | `twist.covariance` | элемент [0] равен дисперсии скорости, (м/с)²; остальные равны 0 |

Координаты x и y даны в той же системе, в которой организаторы строят эталон: проекция UTM, зона 37N (WGS84), со сдвигом `x = E − 300 000`, `y = N − 6 100 000`, в метрах. На этой линии x переходит через 100 000 м, координаты при этом непрерывные. z равна высоте рельса по карте путей в точке `base_link`. Курс отсчитывается от оси x (на восток) против часовой стрелки в направлении движения. В начале поездки к x, y и z добавляется разница между фиксом GNSS и точкой на карте (по высоте с учётом того, что антенна стоит на 3.10 м выше `base_link`). По x и y эта поправка линейно уменьшается до нуля за первые 160 м пути, по высоте за 400 м.

Точка `base_link` — опорная точка вагона в TF организаторов: вертикальная ось поворота передней тележки на уровне контакта колеса с рельсом. На крыше вагона две антенны GNSS, master и rover: master стоит в 9.873 м позади `base_link`, rover в 2.563 м впереди.

`/result/velocity` публикуется с первого годного сообщения тележки. `/result/position` начинает публиковаться, когда нода по GNSS первых секунд нашла трамвай на карте маршрута. Если привязки нет (GNSS не пришёл за 5 с после первого входа или выключен параметром `gnss_init_s:=0`), нода публикует положение относительно точки старта: x равен пройденному пути, y и z равны 0, а `/diagnostics` показывает `WARN`.

Выходы публикуются с надёжной доставкой (reliable) и глубиной очереди 10. Входы нода принимает с доставкой best effort и глубиной очереди 100; такие настройки совместимы и с плеером, и с подпиской скрипта организаторов.

## Как проверить, что всё работает

```sh
ros2 topic hz /result/velocity                                     # частота, ожидается около 30 Гц
ros2 topic echo /result/position --once                            # одно сообщение положения
ros2 topic echo /diagnostics --once                                # состояние оценки
```

Раз в 30 секунд нода пишет в лог строку вида `published 1590, duplicate stamps skipped 32, estimator errors 0, gnss window closed`: сколько оценок опубликовано, сколько повторных меток пропущено, сколько раз ядро выбросило исключение и закрыто ли окно GNSS. Когда окно закрывается, нода пишет `GNSS alignment window closed: GNSS speed unsubscribed, later fixes ignored`.

Эти строки видны в терминале `ros2 launch` и сохраняются в файле `~/.ros/log/python3_<pid>_<время>.log`, где `<pid>` берётся из строки launch `process started with pid [...]`. В папке запуска `~/.ros/log/<дата>-<хост>-<pid>/launch.log` строк ноды нет (в launch-файле задано `output="screen"`).

Топик `/diagnostics` имеет стандартный тип `diagnostic_msgs/msg/DiagnosticArray` и приходит 2 раза в секунду по системным часам. В сообщении один статус с именем `tram_odometry/estimator`. Топик понимают обычные инструменты ROS, например `rqt_robot_monitor`. Он собирается вне обработчиков входов и на `/result/*` не влияет. Основные поля:
- `mode`: значение из двух частей, например `route/wheels`. Первая часть говорит, привязано ли положение к маршруту (`route`) или считается от старта (`relative`). Вторая часть говорит, откуда скорость: колёса в норме (`wheels`), доверие к колёсам снижено (`slip`) или свежих скоростей тележек нет и скорость ведёт одна модель тяги (`model`). До первой оценки значение `init`;
- `slip_front`, `slip_rear`: идёт эпизод проскальзывания на передней или задней тележке;
- `weight_front`, `weight_rear`: последний вес измерения тележки в фильтре, от 0 до 1;
- `longitudinal_slip_front`, `longitudinal_slip_rear`: продольное проскальзывание `(v_тележки / wheel_scale − v) / max(v, 0.5 м/с)`, плюс при буксовании, минус при юзе; ключ есть, только если сообщение тележки не старше 0.5 с и режим не `model`;
- `localized`, `path_id`, `s_route`: привязано ли ядро к маршруту, номер пути в карте (−1 до привязки) и положение на этом пути, м;
- `gnss_window`: состояние окна GNSS: `waiting` (GNSS ещё не было), `open`, `closed`, `none` (GNSS не пришёл за 5 с после первого входа) или `disabled`;
- `published`, `core_errors`: сколько оценок опубликовано и сколько раз ядро выбросило исключение.

Уровень статуса:
- `OK`: замечаний нет;
- `WARN`: идёт эпизод проскальзывания или снижено доверие к колёсам; от одной тележки нет сообщений 0.5 с и дольше (по меткам входов); скорость ведёт одна модель тяги; положение публикуется относительно старта, потому что привязки к маршруту нет;
- `ERROR`: за последние 5 с ядро выбросило исключение; нода его перехватила и продолжает работать;
- `STALE`: оценок ещё не было или больше 2 с не приходили входы.

## Параметры

Параметры ноды лежат в `src/tram_odometry/config/params.yaml`. Launch-файл читает установленную копию этого файла (`install/tram_odometry/share/tram_odometry/config/params.yaml`), поэтому после правки в `src/` пакет нужно собрать заново, как в разделе 1. Без пересборки можно передать свой файл: `ros2 launch tram_odometry tram_odometry.launch.py params_file:=<путь к файлу.yaml>`.

Длительность окна GNSS задаёт аргумент запуска `gnss_init_s:=<секунды>`, по умолчанию 5.0. Launch-файл передаёт его ноде после файла параметров, поэтому значение `gnss_init_s` в `params.yaml` при запуске через launch не действует. `gnss_init_s:=0` отключает GNSS полностью, и тогда положение считается относительно точки старта. Остальные параметры описаны в [разделе 4](4_params.md).

## Метрики, задержка и ресурсы

### Точность: скрипт организаторов

Скрипт `hackathon_solution_checker` сравнивает `/result/velocity` и `/result/position` с эталоном `/localization/kinematic_state`. Этот эталон есть только в проверочной записи организаторов `30618_88aea4d9`, в записях датасета его нет. Скрипт собирается в своём workspace (почему не вместе с решением, сказано выше) и запускается до проигрывания записи:

```sh
# терминал 3: скрипт организаторов, в их workspace
source /opt/ros/humble/setup.bash
cd <папка скрипта организаторов>
colcon build --packages-select tram_vehicle_msgs hackathon_solution_checker
source install/setup.bash
ros2 run hackathon_solution_checker metrics
```

Порядок такой: скрипт, нода, `ros2 bag play -d 2`. Скрипт печатает RMSE и максимум ошибки каждые 5 с и итог после Ctrl+C. В итоге нужно смотреть строку `distance: RMSE=…` (3D-ошибка положения, м) и `velocity: RMSE=…` (м/с).

### Задержка, частота и ресурсы: `tools/latency_probe.py`

Метка `header.stamp` в выходе равна метке входа из записи, то есть времени записи рейса. Поэтому `ros2 topic delay` показывает не задержку ноды, а возраст записи. Задержку меряет скрипт `tools/latency_probe.py` из этой папки. Он подписывается на входы и выходы ноды и для каждого выхода считает, сколько прошло от прихода последнего входа с той же меткой до прихода выхода. Оба момента он фиксирует сам, так что в задержку входит и доставка через ROS 2 в обе стороны. Скрипту нужны только `rclpy` и наш `tram_vehicle_msgs`.

```sh
# терминал 4: замер, запустить до ros2 bag play
source /opt/ros/humble/setup.bash && source install/setup.bash
python3 tools/latency_probe.py
```

Каждые 30 с и в конце скрипт печатает по каждому выходу число сообщений, частоту, `frame_id`, медиану, 95-й процентиль и максимум задержки, а для `/result/position` ещё `child_frame_id` и число сообщений с заполненными ковариациями. В Linux он находит процесс `odometry_node` и раз в секунду снимает его загрузку процессора (в ядрах) и память (RSS, МиБ). Скрипт сам завершается через 10 с после последнего выхода ноды или по Ctrl+C.

Так мы проверили решение 27.09.2026 на проверочной записи `30618_88aea4d9` (21.8 мин). Контейнер был собран по Dockerfile из пакета проверки организаторов (`ros:humble-ros-base`), с отключённой сетью и 2 ядрами. В него положили только эту папку. Замер шёл с 3-й минуты записи до конца:

| Величина | `/result/velocity` | `/result/position` |
|---|---|---|
| сообщений в замере | 33 981 | 33 981 |
| частота, Гц | 29.3 | 29.3 |
| задержка, медиана, мс | 0.68 | 1.06 |
| задержка, 95-й процентиль, мс | 2.15 | 2.77 |
| задержка, максимум, мс | 60.2 | 61.0 |

Все сообщения положения пришли с `frame_id` `map`, `child_frame_id` `base_link` и заполненными ковариациями. Процесс `odometry_node` занимал 0.09 ядра (95-й процентиль, максимум 0.12), память RSS не превышала 68.4 МиБ. Это память одного процесса ноды; вместе с процессом `ros2 launch` наш стенд видел около 105 МиБ. Максимум задержки около 60 мс получается, когда нода ждёт второе сообщение тележки с той же меткой: ожидание длится не дольше 50–60 мс.

Условие задачи требует задержку не больше 100 мс (пик до 250 мс), частоту не ниже 10 Гц, не больше 2 ядер и 0.5 ГБ памяти.

### Визуализация: `tools/viz/`

Визуализатор прогоняет ядро решения на записи офлайн, так же как нода, и строит HTML-страницу: карта с треком и эталоном, скорости тележек и наша скорость, позиция контроллера, веса тележек в фильтре, эпизоды проскальзывания, привязки к карте, ошибки вдоль и поперёк пути. Он работает в том же окружении ROS 2, pip-пакеты не нужны:

```sh
source /opt/ros/humble/setup.bash && source install/setup.bash
python3 tools/viz/org_ref.py <каталог с записями>/30618_88aea4d9 viz_ref
python3 tools/viz/viz.py 30618_88aea4d9 --data <каталог с записями> --ref viz_ref --out 30618_88aea4d9.html --check
```

`org_ref.py` берёт эталон из топика организаторов `/localization/kinematic_state`. Для записи без этого топика запускайте `viz.py` без `--ref`, тогда страница будет без графиков ошибки. Ключ `--check` дополнительно сверяет выходы ядра с прогоном без съёма внутренних величин бит в бит. Для открытия страницы браузеру нужен интернет (plotly.js с cdnjs). Готовая страница проверочной записи лежит в `tools/viz/examples/`, описание разделов страницы в `tools/viz/README.md`.

### Как получены таблицы раздела 5

Числа по 25 записям датасета в [разделе 5](5_results.md) и таблицы в `docs/results/` мы получили своим стендом. В эту папку он не входит. Стенд проигрывает каждую запись в отдельном контейнере без сети, оставляя ноде три входа и GNSS первых 5 с. Решению он выделяет 2 ядра и 512 МиБ памяти, а выход сравнивает с GNSS антенны master, перенесённым в точку `base_link` по TF организаторов. Задержку стенд считает так же, как `tools/latency_probe.py`.
